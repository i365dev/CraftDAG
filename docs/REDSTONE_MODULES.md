# Redstone modules: evidence and boundary

CraftDAG has two independently verified MinePilot modules: `ItemSorterSlice` and a Java quasi-connected `PistonDoor`. Their static layouts establish a small shared structural kernel. Their behavior remains module-specific and is verified downstream in the official runtime.

## Comparison of the verified implementations

The evidence sources are MinePilot [PR #134](https://github.com/i365dev/MinePilot/pull/134) for ItemSorterSlice and [PR #136](https://github.com/i365dev/MinePilot/pull/136) for PistonDoor (merged MinePilot commit `171926a535389a3446dcc9a1f4ca52f0a38e8afc`). CraftDAG's compact fixtures retain the static topology and four expected orientations, with provenance back to those proofs.

| Concept | Shared structural evidence | Module-specific or external evidence |
| --- | --- | --- |
| Identity/version | Both have a stable module id and version. | The ids and versioning schemes are independent. |
| Canonical layout | Both define integer local coordinates, canonical bounds/facing, and role-tagged authored blocks. | Bounds and authored roles differ. |
| Block states | Both store concrete Minecraft block IDs and exact string properties. | Sorter uses hopper/comparator/repeater/wire/torch states; PistonDoor uses lever/piston states and relies on quasi-connectivity. |
| Orientation | Both rotate local coordinates, bounds, and horizontal `facing` deterministically. | ItemSorter also uses compass-key wire properties, which the kernel rotates. During non-zero turns only those directions and verified invariant properties are accepted; unknown properties fail closed. |
| Generic structure checks | Both use bounded coordinates and non-colliding occupied cells; roles identify authored blocks. | The kernel also requires unique valid role IDs. Required-role relationships and topology invariants remain module-specific. |
| VoxelPlan/provenance | Both lower to ordinary VoxelPlan blocks and carry roles through `sourceNodeId`. Identity/version is reflected in the plan name. | Runtime receipts, artifact digests, references, and behavioral claims remain in downstream evidence. |
| Reference conformance | Both were compared with an external reference. | The sorter has a reference block-table check; the door has an independent six-block reference gate and candidate/reference mechanical check. |
| Runtime semantics | Both have exact external runtime verification evidence. | Sorter initialization, item routing, threshold behavior, and inventory assertions are sorter-specific. Piston movement, reset/pullback, and quasi-connectivity are door-specific. |
| Ports and timing | No repeated public contract was proved. | Ports, signal graphs, timing semantics, and a generic scenario model remain unsupported. |

## Proven shared kernel

The internal experimental helper in `packages/core/src/redstone/moduleKernel.ts` accepts a canonical bounded static topology with:

- module identity and version;
- canonical facing and positive integer bounds;
- unique role-tagged blocks at local integer coordinates;
- concrete `minecraft:*` block IDs and exact string properties.

It validates bounds, roles, collisions, and requested facings; rotates coordinates, bounds, horizontal `facing`, and compass-key properties for north/east/south/west; and lowers to the existing VoxelPlan shape. During non-zero rotations, `face`, `enabled`, `extended`, `lit`, `locked`, `mode`, `power`, `powered`, `type`, `waterlogged`, and `delay` are preserved because they occur in the verified fixtures as non-directional state. Any other property fails closed; with zero rotation properties remain unchanged. Block roles are preserved in `sourceNodeId`. Output blocks retain concrete IDs and states. The helper is experimental and is not exported from the public package entry point.

Compact static regression fixtures at `packages/core/test/fixtures/redstone/` preserve both canonical topologies and all four expected facing outputs. Tests compare kernel output against these checked-in values; expected transforms are not generated by the code under test. Fixtures contain no GameTest code, server packs, reports, logs, or artifact trees.

## Module-specific semantics and verification

The kernel does not validate circuit behavior or infer topology. Keep these rules with each module and its downstream verifier:

- **ItemSorterSlice:** filter inventory initialization, transport/overflow path, hopper and comparator relationships, threshold/repeater/torch behavior, and matching/non-matching item routing.
- **PistonDoor:** piston arrangement, moved blocks, activation/reset order, sticky pullback, and Java quasi-connectivity.
- **Verification:** MinePilot's official runtime receipts, state-exact schematic round trips, GameTest assertions, and module-specific reference comparisons remain external evidence. CraftDAG's regression tests prove static compilation and state preservation; they do not rerun Minecraft behavior.

## Runtime-target boundary

Current VoxelPlan output contains concrete Minecraft block IDs and block-state properties. It is not edition-neutral. The completed #131 boundary remains in force: shared logical intent may lower to target-specific Redstone topology. The verified PistonDoor depends on Java quasi-connectivity, so its topology cannot be claimed portable to Bedrock. No Java-to-Bedrock mapping or public RuntimeTarget API is introduced here.

## Explicitly deferred

The two proofs do not establish support for:

- public ports or generic signal inputs/outputs;
- signal graphs, automatic Redstone routing, or arbitrary circuit synthesis;
- timing, tick, or generic runtime-scenario DSLs;
- module composition or repetition semantics;
- Bedrock topology mapping or edition-neutral VoxelPlan;
- a public `RedstoneModulePlan` API.

Add such abstractions only when further real evidence justifies them. Do not infer them from these two modules.
